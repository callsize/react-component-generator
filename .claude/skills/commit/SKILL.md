# commit: 변경사항 분석 → 컨벤션 커밋

## 커밋 메시지 컨벤션

형식: `<type>: <한국어 요약>`

| type | 용도 |
| --- | --- |
| `feat` | 새 기능, UI/디자인 추가·개선 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `chore` | 설정, 의존성, 빌드, 문서 등 기타 |

- 요약은 한 줄, 50자 안팎, 마침표 없이 명사형/동사형으로 간결하게 쓴다.
- "무엇을 왜 했는지"가 필요하면 빈 줄 뒤 본문에 한국어 불릿으로 적는다.
- 코드 식별자·파일명·기술 용어는 원문 그대로 둔다.

## 절차

### 1. 변경사항 분석

다음을 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff              # unstaged
git diff --staged     # staged
git log --oneline -5  # 기존 메시지 스타일 참고
```

- git 저장소가 아니거나 변경이 없으면 그 사실만 알리고 종료한다.
- untracked 파일은 내용을 읽어 성격을 파악한다.
- `.env`, 키·토큰, 인증서 등 비밀 정보로 보이는 파일이 있으면 커밋 대상에서 제외하고 사용자에게 경고한다. `node_modules`, 빌드 산출물도 제외한다.

### 2. 논리적 단위로 분류

- 하나의 목적(기능 하나, 버그 하나)으로 묶이는 파일끼리 한 커밋으로 만든다.
- 서로 다른 type(예: 기능 추가와 설정 변경)이 섞여 있으면 분리한다.
- 한 파일 안에서 목적이 섞여 있어도 hunk를 쪼개지 않고, 파일 단위로 가장 가까운 커밋에 포함한다.
- 변경이 한 덩어리면 커밋 1개로 충분하다. 억지로 나누지 않는다.

### 3. 커밋 메시지 작성

각 커밋 단위마다 type과 한국어 요약을 작성한다. 커밋하기 전에 다음 형태로 계획을 출력한다. 승인을 기다리지 않는다.

```
커밋 1/2  feat: 레트로 테마 적용 및 레이아웃 개선
  - src/App.css
  - src/index.css
  - index.html
커밋 2/2  chore: commit 스킬 추가
  - .claude/skills/commit/SKILL.md
```

### 4. 바로 커밋

- 사용자 승인 없이 계획대로 즉시 커밋한다. 확인 질문을 하지 않는다.
- 커밋 단위별로 파일을 **명시적으로** stage 한다. `git add -A`, `git add .`는 쓰지 않는다.
- 커밋 후 `git log --oneline -n <커밋 수>`로 결과를 보여준다.
- 시스템 지시에 커밋 attribution 줄이 있으면 메시지 끝에 덧붙인다.

## 금지 사항

- `git push`, `--amend`, `--no-verify`, force 관련 옵션은 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다.
- pre-commit hook이 실패하면 우회하지 말고 원인을 보고하고 수정한 뒤 새 커밋으로 만든다.
