# TDD Rule

**이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 1. 적용 기준

### TDD 필수

- **비즈니스 로직**: 도메인 규칙, 계산, 상태 전이, 데이터 변환
- **API**: 엔드포인트, 요청/응답 처리, 에러 분류, 외부 서비스 호출 래퍼
- **유틸 함수**: 순수 함수, 파서, 포매터, 폴백/재시도 로직
- **버그 수정**: 버그를 재현하는 실패 테스트를 **먼저** 작성한 뒤 고친다

### TDD 불필요

- **타입 정의**: `type`, `interface` 선언만 있는 파일
- **설정 파일**: `vite.config.ts`, `tsconfig*.json`, `eslint.config.js`, `package.json` 등
- **순수 UI**: 로직 없이 마크업과 스타일만 있는 컴포넌트, CSS 변경
- **SQL**: 스키마, 마이그레이션, 쿼리 스크립트

경계가 모호하면(분기나 상태가 있는 UI 등) **TDD를 적용한다.**

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 테스트는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류, 잘못된 셋업으로 인한 실패는 RED로 인정하지 않는다. 테스트를 고쳐서 올바른 이유로 실패시킨다.
- 테스트가 처음부터 통과하면 그 테스트는 아무것도 검증하지 못한다. 폐기하고 다시 쓴다.

### GREEN: 최소 구현

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 아직 테스트가 요구하지 않는 분기, 옵션, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트 전체**를 실행해 모두 통과하는지 확인한다. 하나라도 실패하면 GREEN이 아니다.

### REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 매 변경 후 테스트를 실행해 **green을 유지**한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 반복

다음 동작에 대한 **RED로 돌아간다.** 요구사항의 동작이 모두 테스트로 덮일 때까지 반복한다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 임시 파일 보관, 복사해 두기, 보면서 다시 쓰기 모두 포함한다. 기억에서 다시 구현하는 것까지만 허용한다.
- 삭제 후 첫 단계는 항상 실패하는 테스트 작성이다.

## 4. 변명 차단표

| 변명 | 반론 |
| --- | --- |
| 너무 단순해서 테스트 불필요 | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 단순한 코드가 가장 자주 조용히 깨진다. |
| 나중에 추가하겠다 | 나중은 오지 않는다. 구현 후 작성한 테스트는 구현을 베끼므로 버그를 못 잡는다. |
| 시간이 없다 | 테스트 없는 코드의 디버깅과 회귀 수정이 더 오래 걸린다. 시간이 없을수록 사이클을 지킨다. |
| 삭제하면 낭비다 | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 쪽이 더 큰 낭비다. |
| 프로토타입이다 | 프로토타입은 그대로 프로덕션이 된다. 버릴 코드라면 테스트 없이 쓰되 **커밋하지 않고 폐기**한다. |

## 5. 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- **이 파일은 기본값(fallback)** 이다. 프로젝트 규칙이 다루지 않는 부분에만 적용한다.
- 충돌 시 프로젝트 규칙을 따르고, 이 파일의 해당 조항은 무시한다.
